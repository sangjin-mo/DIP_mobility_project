# 테스트 가이드

> 대상: `features/stop_sign/system/` (정지 표지판 인식 시스템, 2호기 쪽)
> 설계 배경이 궁금하면 [`../../design/README.md`](../../design/README.md) 참고.
> 1호기(실제로 모터를 정지·재개하는 쪽)는 이 리포지토리 범위 밖입니다 —
> 여기서는 **2호기가 표지판을 정상적으로 인식하고, 정해진 규칙대로 정지 요청을 보내는지**까지만 확인합니다.

> ⚠️ **2026-08-23 구조 변경**: 정지 신호가 더 이상 GPIO 핀 직결이 아닙니다 — 점퍼케이블 연결이 물리적으로 불가능해져 폐기됐고, 지금은 2호기가 **central 서버(`192.168.2.175:8080`, PC의 `web_dashboard`)에 HTTP로 정지/재출발 요청을 보내는 방식**입니다. (출처: `stop_sign/pi2_detector/config.py`·`mediapipe/pi2_gesture/gesture_config.py`의 `DASHBOARD_URL` — `../../design/README.md` §8, `../../../mediapipe/design/README.md` §3-1-1 참고) **예전에 이 컴퓨터에서 로컬로 확인할 때는 이 컴퓨터의 그때그때 IP**(예: `192.168.2.94`)**를 `web_dashboard` 주소로 썼는데**, 이제는 코드에 `192.168.2.175`가 고정돼 있어 그 값이 아니면 정지 요청이 central 서버로 안 갑니다. 아래 안내를 그에 맞게 갱신했습니다.

## 0. 시작 전에 알아둘 것

이 테스트는 **라즈베리파이 2호기 하나**에서 진행합니다 (1호기·central 서버 연동은 별도).

| 확인할 것 | 왜 |
|---|---|
| 2호기에 측면 카메라(USB 웹캠)가 연결돼 있는지 | 카메라가 없으면 `detector.py`가 시작하자마자 에러로 종료됩니다 |
| 2호기가 켜져 있고 같은 Wi-Fi에 연결돼 있는지 | SSH 접속·상태 API 호출에 필요 |
| `config.py`의 `SIDE_CAMERA_INDEX` 값이 실제 환경과 맞는지 | 지금은 플레이스홀더 값입니다 (design/README.md §8 참고). **GPIO 핀 설정은 이제 없습니다** — GPIO 경로 자체가 폐기됐습니다 |
| `GESTURE_RECOGNITION_ENABLED`(`config.py`)가 `False`인지 | 2호기 실기에서 mediapipe 공식 패키지가 SIGILL로 크래시하는 문제 때문에 지금은 꺼둔 상태가 정상입니다. `True`로 바꾸면 이 크래시가 재현될 수 있습니다 |

> ℹ️ **정지 결과를 눈으로 확인하려면**: 예전처럼 LED를 달 필요 없이, central 서버(`http://192.168.2.175:8080/`)의 대시보드 화면을 열어두면 정지/재출발 시 화면 상태(RUNNING/STOPPED)가 바뀌는 걸 바로 볼 수 있습니다. central 서버 없이 2호기 로그만으로도 아래 3번처럼 "STOP 요청" 로그로 확인 가능합니다.

## 2. "주행 중" 상태로 바꿔서 추론 켜기

> ⚠️ **동작 방식이 바뀌었습니다**: `detector.py`는 이제 `set_vehicle_state.ps1`의 push를 그냥 기다리지 않고, **1초마다 스스로 central 서버(`192.168.2.175:8080`)의 `/api/control/status`를 폴링해서 `driving` 값을 계속 덮어씁니다.** 즉 아래 방법 중 하나를 상황에 맞게 고르세요.

### 방법 A. central 서버가 켜져 있는 경우 (권장, 별도 조작 불필요)

central 서버(`http://192.168.2.175:8080/`)의 대시보드에서 **START**를 눌러 상태를 `RUNNING`으로 만들면, 최대 1초 안에 `detector.py` 창에 아래 로그가 자동으로 뜹니다:
```
[detector] driving=True 로 전환
```
따로 `set_vehicle_state.ps1`을 실행할 필요가 없습니다 — 오히려 실행해도 다음 폴링 주기(최대 1초 후)에 central 서버 상태로 다시 덮어써집니다.

### 방법 B. central 서버 없이 2호기만 단독으로 테스트하는 경우

이 경우 폴링이 매번 실패해서 `driving`이 계속 `False`로 되돌아가므로, **`set_vehicle_state.ps1`로 push해도 1초 안에 원상복구되어 사실상 안 먹힙니다.** 수동으로 값을 유지하려면, 2호기의 `config.py`에서 `DRIVING_STATE_POLL_INTERVAL_S`를 테스트 동안만 크게(예: `3600`) 바꾸고 `detector.py`를 재시작한 뒤 아래를 실행하세요 (테스트 끝나면 원래 값 `1.0`으로 복원):

```
cd "C:\Users\js033\hee\SW플랫폼_모빌리티_프로젝트\features\stop_sign\system\testguide"
powershell -ExecutionPolicy Bypass -File .\set_vehicle_state.ps1 -Driving true
```

`detector.py`가 떠 있는 창에 아래 로그가 뜨면 성공입니다:
```
[detector] driving=True 로 전환
```

이제부터 카메라 프레임을 읽고 실제로 YOLO 추론을 시작합니다.

## 3. 표지판 인식 확인하기

카메라 앞에 정지 표지판(프린트물이든 화면에 띄운 것이든 상관없음)을 가까이 대면, `config.py`의 `DEBOUNCE_N` 프레임만큼 연속으로 잡혔을 때 아래 로그가 뜹니다:

```
[detector] 표지판 확정 — STOP 요청 (쿨다운 5.0s 시작)
[control] STOP 전송 완료 (사유={'STOP_SIGN'})
```

(central 서버가 꺼져 있거나 연결이 안 되면 두 번째 줄 대신 `[control] STOP 전송 실패: ...`가 뜹니다 — 표지판 인식 자체는 정상 동작한 것이니 이 경우는 §0의 central 서버 연결 여부를 먼저 확인하세요.)

표지판을 치우고 `DEBOUNCE_M` 프레임만큼 연속으로 안 잡히면:

```
[detector] 표지판 해제 — STOP 요청 철회
[control] START 전송 완료 (속도 0.25 m/s 복원)
```

- central 서버 대시보드(`http://192.168.2.175:8080/`)를 열어두면, 위 로그와 동시에 화면 상태가 `RUNNING → STOPPED → RUNNING`으로 바뀌는 것도 같이 확인할 수 있습니다. (GPIO/LED는 더 이상 안 씁니다 — §0 참고)
- "STOP 요청" 로그가 뜬 직후 바로 표지판을 다시 대도, 쿨다운 시간(`COOLDOWN_SECONDS`) 동안은 새 요청이 안 뜨는 게 정상입니다 (§3-1 재정지 방지 로직).

## 4. "정지" 상태로 되돌려서 추론 끄기 확인

central 서버 대시보드에서 **STOP**을 누르면 최대 1초 안에 자동으로 `driving=False`가 됩니다 (§2 방법 A). central 서버 없이 단독 테스트 중이라면(§2 방법 B):

```
powershell -ExecutionPolicy Bypass -File .\set_vehicle_state.ps1 -Driving false
```

`detector.py` 창에 `driving=False 로 전환` 로그가 뜨고, 그 뒤로는 표지판을 갖다 대도 아무 반응이 없어야 정상입니다 (추론 자체를 생략하는 중이므로).

## 5. 끝나면 정리하기

`detector.py`가 떠 있는 창(SSH 접속 창)에서 `Ctrl+C`를 눌러 종료합니다.

## 테스트 시나리오 예시

1. `detector.py` 실행 → `driving=False`로 대기 상태 확인
2. central 서버 대시보드에서 START (또는 §2 방법 B로 `set_vehicle_state.ps1 -Driving true`) → `driving=True` 전환 확인
3. 표지판을 카메라에 가까이 대기 → `STOP 요청`/`[control] STOP 전송 완료` 로그 확인 (central 서버 대시보드 열어뒀으면 화면도 STOPPED로 바뀌는지 확인)
4. 표지판을 치움 → `STOP 요청 철회`/`[control] START 전송 완료` 로그 확인
5. STOP 직후 바로 다시 표지판을 대봐서, 쿨다운 시간 동안 재신호가 안 뜨는지 확인
6. central 서버 대시보드에서 STOP (또는 `set_vehicle_state.ps1 -Driving false`) → 표지판을 대도 반응 없는지 확인 (자원 절약 로직 검증)

## 문제가 생겼을 때

| 증상 | 원인 후보 | 확인 방법 |
|---|---|---|
| `detector.py` 실행하자마자 카메라 에러로 종료 | `SIDE_CAMERA_INDEX`가 실제 장치 번호와 다름 | 2호기에서 `v4l2-ctl --list-devices`로 실제 인덱스 확인 후 `config.py` 수정 |
| `detector.py` 실행하자마자 mediapipe 관련 크래시(`SIGILL`, `aes enabled`) | `config.py`의 `GESTURE_RECOGNITION_ENABLED`가 실수로 `True`로 바뀜 | `False`로 되돌리기 — 이 Pi(Cortex-A72, AES 미지원)에서 공식 mediapipe가 원천적으로 크래시함(`mediapipe/design/README.md` §4-5) |
| `set_vehicle_state.ps1` 실행 시 연결 실패 | `detector.py`가 안 켜져 있거나, 2호기 IP가 바뀌었거나, 방화벽이 8010 포트를 막음 | `detector.py` 창이 살아있는지 확인, `$PI_IP` 값 확인, 2호기 방화벽에서 8010 인바운드 허용 확인 |
| `set_vehicle_state.ps1 -Driving true`를 실행했는데 `driving=True`가 금방 다시 `driving=False`로 돌아옴 | **버그 아님** — central 서버가 없거나 응답이 없으면 1초마다 도는 폴링이 매번 실패로 처리되어 `driving=False`로 되돌림(§2) | central 서버 없이 테스트 중이면 §2 방법 B대로 `DRIVING_STATE_POLL_INTERVAL_S`를 임시로 늘려서 재시작 |
| `[control] STOP 전송 실패: ...` 로그가 뜸 | central 서버(`192.168.2.175:8080`)에 연결이 안 됨 | central 서버가 켜져 있는지, 이 Pi와 같은 네트워크인지 확인 — 표지판 인식 자체는 정상이므로 급한 문제는 아님 |
| 표지판을 대도 `STOP 요청` 로그가 안 뜸 | `driving=False` 상태이거나, confidence가 임계값(`CONFIDENCE_THRESHOLD`)에 못 미침 | 2번 단계로 돌아가 `driving=True` 확인, 표지판을 더 가까이/정면으로 대보기 |
