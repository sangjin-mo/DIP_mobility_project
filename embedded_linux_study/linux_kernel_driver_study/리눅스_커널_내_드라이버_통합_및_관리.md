# 리눅스 커널 내 드라이버 통합 및 관리

## 1. 보고서 개요

### 1.1 수행 목표

본 학습의 목적은 문자 디바이스 드라이버를 외부 커널 모듈로만 빌드하는 단계를 넘어 Linux 커널 소스 트리에 통합하고, Kconfig와 kbuild를 이용해 내장 드라이버 또는 모듈로 선택하여 빌드·관리하는 방법을 익히는 것이다.

- 드라이버와 커널의 상호작용 및 시스템 자원 사용 방식을 이해한다.
- 소스, Kconfig, Makefile을 커널 트리에 통합한다.
- Raspberry Pi 4용 커널 이미지에 드라이버를 내장하고 부팅 후 확인한다.
- 메모리, 오류 처리, 인터럽트, 동시성, 의존성 관점에서 안정성을 평가한다.
- 통합 전후의 이미지 크기, 부팅 시간, 메모리 및 로그를 비교한다.

> **실습 범위:** 이 문서와 동봉 소스는 통합 가능한 형태로 작성·정적 검토하였다. 현재 작성 환경은 Windows이며 Linux 커널 소스, ARM64 크로스 컴파일러 및 Raspberry Pi 4가 연결되어 있지 않으므로 실제 커널 전체 컴파일과 보드 부팅 결과를 임의로 성공했다고 기록하지 않는다. 아래 검증표는 Linux 개발 PC와 보드에서 직접 작성해야 한다.

## 2. 드라이버 통합의 기본 원리

### 2.1 커널과 드라이버의 상호작용

드라이버는 하드웨어 또는 논리 장치를 커널의 공통 인터페이스에 연결한다. 사용자 프로그램이 `/dev/string_buffer`를 `open`, `read`, `write`, `close`하면 VFS가 `struct file_operations`에 등록된 드라이버 함수를 호출한다. 실제 하드웨어 드라이버라면 여기에 버스의 `probe/remove`, MMIO, IRQ, DMA, 전원 관리가 추가된다.

```text
사용자 프로그램
  open/read/write/close
          │ 시스템 호출
          ▼
VFS 및 문자 장치 계층
  dev_t → cdev → file_operations
          │ 콜백
          ▼
string_buffer 드라이버
  mutex + 256바이트 버퍼
          │
          ├─ class/device → /sys/class 및 /dev 노드
          └─ 실제 장치 드라이버라면 MMIO·IRQ·DMA·PM 사용
```

### 2.2 커널 소스 트리와 빌드 시스템

Linux는 아키텍처 코드, 서브시스템 및 드라이버를 디렉터리로 나누며 Kconfig가 기능 선택과 의존성을 표현하고 kbuild Makefile이 선택 결과를 오브젝트 링크 방식으로 변환한다.

```text
Kconfig 메뉴 선택
   ├─ n : 빌드 제외
   ├─ m : loadable module(.ko)
   └─ y : built-in.a → vmlinux → Image
                  │
                  └─ 부팅 중 module_init()에 대응하는 initcall 실행
```

이번 실습의 통합 위치는 다음과 같다.

```text
linux/drivers/char/string_buffer/
├─ Kconfig
├─ Makefile
└─ string_buffer.c
```

상위 `drivers/char/Makefile`에는 아래 항목을 넣는다.

```make
obj-$(CONFIG_STRING_BUFFER_DRIVER) += string_buffer/
```

하위 `drivers/char/string_buffer/Makefile`은 다음과 같다.

```make
obj-$(CONFIG_STRING_BUFFER_DRIVER) += string_buffer.o
```

상·하위에서 같은 심볼을 사용하므로 값이 `y`이면 하위 오브젝트가 커널에 내장되고, `m`이면 `string_buffer.ko`가 된다. 상위 디렉터리가 `m`으로 방문됐는데 하위 파일을 `obj-y`에만 넣으면 내장 아카이브가 커널에 링크되지 않아 고아 오브젝트가 될 수 있다. 링크 순서는 initcall 호출 순서에도 영향을 줄 수 있으므로 Makefile 항목의 순서를 무의미하게 재정렬하지 않는다.

### 2.3 내장 드라이버와 모듈 비교

| 항목 | 커널 내장 `=y` | 모듈 `=m` |
|---|---|---|
| 사용 시점 | 부팅 초기부터 사용 가능 | 모듈 로더 또는 사용자가 적재한 뒤 사용 |
| 루트 파일 시스템 | 장치 접근에 반드시 필요한 드라이버에 유리 | initramfs에 모듈과 의존성을 넣으면 가능 |
| 메모리 | 런타임 동안 상주 | 언로드 가능한 경우 회수 가능 |
| 갱신 | 커널 재빌드·재부팅 필요 | ABI가 맞으면 모듈 교체·재적재 가능 |
| 장애 영향 | 초기화 실패·결함이 부팅 전체에 영향 가능 | 격리는 제한적이나 적재 시점 제어 가능 |
| 확인 방법 | `dmesg`, `/proc/devices`, `vmlinux`; `lsmod`에는 없음 | `lsmod`, `modinfo`, `dmesg` |
| 심볼 접근 | 커널 링크 시 해석되나 내부 API 결합은 피해야 함 | `EXPORT_SYMBOL*`로 공개된 심볼만 사용 가능 |

부팅의 기초가 되는 아키텍처 초기화, 스케줄러·메모리 관리·VFS 핵심, 인터럽트/시간 계층의 기반 기능은 일반적인 모듈로 분리하기 어렵다. 루트 파일 시스템을 읽는 데 필요한 저장장치·파일 시스템 드라이버도 initramfs가 제공하지 않는다면 내장해야 한다. 단, “항상 내장” 여부는 부팅 구조와 해당 Kconfig 의존성에 따라 달라진다.

## 3. 제공 문자 드라이버의 구조

### 3.1 동작

동봉된 `string_buffer.c`는 다음 기능을 제공한다.

- `alloc_chrdev_region()`으로 메이저/마이너 번호를 동적 할당한다.
- `cdev_add()`로 문자 장치를 등록한다.
- class와 device를 생성하여 udev가 `/dev/string_buffer`를 만들 수 있게 한다.
- `write()`는 사용자 문자열을 최대 255바이트까지 저장한다.
- `read()`는 최근 저장 문자열을 파일 오프셋에 따라 반환한다.
- mutex로 여러 프로세스의 동시 읽기·쓰기를 직렬화한다.
- 각 단계가 실패하면 역순으로 이미 확보한 자원을 해제한다.

256바이트 배열에서 마지막 1바이트는 NUL 종료용으로 남긴다. 256바이트 이상의 쓰기는 255바이트의 짧은 쓰기로 반환되므로 사용자 프로그램은 반환값을 확인해야 한다. 커널은 문자열 종료가 아니라 `data_length`로 유효 데이터 길이를 관리한다.

### 3.2 초기화와 오류 복구 흐름

```text
alloc_chrdev_region
        │ 실패 → 반환
        ▼
     cdev_add
        │ 실패 → dev 번호 해제
        ▼
   class_create
        │ 실패 → cdev 삭제 → dev 번호 해제
        ▼
   device_create
        │ 실패 → class/cdev/dev 번호 역순 해제
        ▼
      사용 가능
```

모듈 모드에서는 `rmmod` 때 정리 함수가 실행된다. 내장 모드에서는 일반 운용 중 언로드할 수 없으며 종료 함수에 의존해 자원을 회수하는 설계를 해서는 안 된다.

## 4. 커널 소스에 통합하는 절차

### 4.1 사전 준비

Linux 개발 PC에 대상 보드와 동일한 계열의 커널 소스 및 ARM64 크로스 컴파일러를 준비한다. Raspberry Pi 커널 버전, 부트 펌웨어, Device Tree 및 모듈 디렉터리 버전이 서로 일치해야 한다.

```bash
cd ~/src/linux
git status --short
git describe --always --dirty
aarch64-linux-gnu-gcc --version
```

기존의 정상 부팅 커널, DTB, overlay, `/boot/config.txt` 또는 배포판별 부트 설정, 루트 파일 시스템의 `/lib/modules/<release>`를 백업한다. 원격 접속만 가능한 보드에서는 실패 시 복구할 직렬 콘솔 또는 예비 MicroSD를 준비한다.

### 4.2 소스 복사와 상위 파일 수정

동봉 자료의 드라이버 디렉터리를 커널 소스에 복사한다.

```bash
cp -a /path/to/in_tree_driver_integration/drivers/char/string_buffer \
      drivers/char/
```

`drivers/char/Kconfig`의 문자 장치 메뉴 안, 일반적으로 `endmenu` 앞에 다음 줄을 추가한다.

```kconfig
source "drivers/char/string_buffer/Kconfig"
```

`drivers/char/Makefile`에 다음 줄을 추가한다.

```make
obj-$(CONFIG_STRING_BUFFER_DRIVER) += string_buffer/
```

Kconfig의 `tristate`는 `n/m/y`를 허용한다. 새 드라이버는 기본적으로 `default n`으로 두어 명시적으로 선택되게 한다. 실제 하드웨어 의존성이 있다면 `depends on ARM64 && OF`처럼 표현한다. `select`는 선택 대상의 의존성을 검사하지 않으므로 남용하면 잘못된 설정을 만들 수 있다.

### 4.3 Raspberry Pi 4 설정

먼저 보드 기본 설정을 적용하고 그다음 메뉴를 변경한다.

```bash
export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

make bcm2711_defconfig
make menuconfig
```

메뉴에서 다음을 `Y`로 설정한다.

```text
Device Drivers
└─ Character devices
   └─ Educational string-buffer character driver (Y)
```

설정 결과를 확인하고 별도로 보관한다.

```bash
grep '^CONFIG_STRING_BUFFER_DRIVER=' .config
cp .config rpi4_string_buffer.config
make olddefconfig
```

동봉된 `config.fragment`는 자동화 참고용이다. 기존 설정에 단순히 덮어쓰기보다는 `scripts/kconfig/merge_config.sh`로 병합한 뒤 `olddefconfig`와 최종 `grep`으로 확인한다.

### 4.4 전체 커널 빌드

```bash
make -j"$(nproc)" Image modules dtbs
```

빌드 실패 시 첫 오류부터 확인한다. 병렬 빌드 로그가 섞였다면 `make -j1 V=1`로 다시 실행하여 실제 컴파일 명령과 최초 오류를 찾는다.

내장 여부는 다음처럼 확인할 수 있다.

```bash
grep '^CONFIG_STRING_BUFFER_DRIVER=y' .config
grep string_buffer System.map
find . -name 'string_buffer.ko'
```

`=y`이면 심볼은 `vmlinux/System.map`에 존재하고 `.ko`는 생성되지 않는 것이 정상이다. `=m`이면 `string_buffer.ko`가 생성되어야 한다.

### 4.5 MicroSD 배포

배포판마다 부트 파티션 경로와 파일명이 다르므로 현재 보드의 설정을 먼저 확인한다. 기존 커널을 덮어쓰지 말고 새 이름으로 복사한 뒤 부트 설정이 새 이미지를 가리키게 하는 방식을 권장한다.

```bash
# 예시 변수이므로 실제 마운트 지점을 반드시 확인한다.
BOOT=/mnt/rpi-boot
ROOT=/mnt/rpi-root

sudo make modules_install INSTALL_MOD_PATH="$ROOT"
sudo cp arch/arm64/boot/Image "$BOOT/kernel8-string-buffer.img"
sudo make dtbs_install INSTALL_DTBS_PATH="$BOOT/dtbs-string-buffer"
sync
```

Raspberry Pi OS의 펌웨어·커널 구성에 따라 DTB/overlay 설치 위치와 `config.txt` 위치가 달라질 수 있다. 부트 설정에는 실제 생성 파일을 지정하고, 이전 커널로 되돌릴 항목을 남긴다. 커널 이미지와 `/lib/modules/$(make kernelrelease)`가 다른 빌드에서 섞이지 않게 한다.

## 5. 부팅 후 동작 확인

### 5.1 등록 확인

```bash
uname -a
dmesg | grep -i string_buffer
grep string_buffer /proc/devices
ls -l /dev/string_buffer
ls -l /sys/class/string_buffer_class/string_buffer
```

정상 로그 예시는 다음과 같다.

```text
string_buffer: initialized (major=..., minor=0)
```

내장 드라이버는 `lsmod`에 나타나지 않으며 `rmmod` 대상도 아니다. `/dev` 노드가 없다면 먼저 sysfs와 `/proc/devices`를 확인한다. 드라이버가 등록됐지만 udev가 없는 최소 rootfs라면 `/proc/devices`에서 메이저 번호를 확인한 뒤 테스트 목적으로 `mknod /dev/string_buffer c <major> 0`을 사용할 수 있다.

### 5.2 기능 시험

```bash
printf 'embedded-linux' | sudo tee /dev/string_buffer >/dev/null
sudo cat /dev/string_buffer
```

기대 출력은 `embedded-linux`이다. 경계값도 확인한다.

```bash
head -c 255 /dev/zero | tr '\0' A | sudo tee /dev/string_buffer >/dev/null
sudo wc -c /dev/string_buffer

head -c 300 /dev/zero | tr '\0' B | sudo tee /dev/string_buffer >/dev/null
sudo wc -c /dev/string_buffer
```

두 번째 쓰기는 255바이트의 짧은 쓰기가 발생한다. `tee` 같은 프로그램은 남은 데이터를 다시 쓸 수 있으므로 정밀한 반환값 시험은 C 테스트 프로그램 또는 `strace`로 확인한다.

### 5.3 결과 기록표

| 확인 항목 | 기대 결과 | 실제 결과 |
|---|---|---|
| `.config` | `CONFIG_STRING_BUFFER_DRIVER=y` | 실습 후 기록 |
| 전체 빌드 | `Image`, DTB 생성, 오류 0 | 실습 후 기록 |
| 부팅 로그 | 초기화 메시지 1회 | 실습 후 기록 |
| 장치 노드 | `/dev/string_buffer` 문자 장치 | 실습 후 기록 |
| 쓰기/읽기 | 최근 문자열과 동일 | 실습 후 기록 |
| 300바이트 입력 | 한 번의 write는 최대 255바이트 | 실습 후 기록 |
| 경고/오류 | oops, WARN, lockup 없음 | 실습 후 기록 |

## 6. 성능 및 안정성 고려사항

### 6.1 메모리와 수명

- 모든 할당의 소유자와 해제 시점을 명확히 한다.
- 초기화 실패 경로에서 확보한 자원을 역순으로 해제한다.
- 초기화에만 쓰는 함수/데이터에는 `__init`, `__initdata`를 검토한다. 내장 드라이버의 초기화 메모리는 부팅 후 회수될 수 있다.
- 실제 버스 드라이버는 `devm_kzalloc`, `devm_request_irq` 같은 device-managed API를 이용해 `probe()` 실패와 `remove()` 경로를 단순화할 수 있다.
- 사용자 포인터를 직접 역참조하지 않고 `copy_to_user`, `copy_from_user` 또는 검증된 helper를 사용한다.

### 6.2 인터럽트 처리

현재 예제는 논리 장치라 IRQ를 사용하지 않는다. 하드웨어 드라이버로 확장할 때는 다음을 지킨다.

- top half에서는 원인 확인·acknowledge와 최소 상태 저장만 수행한다.
- 오래 걸리거나 sleep이 필요한 일은 threaded IRQ, workqueue 등으로 넘긴다.
- 공유 IRQ에서는 반드시 자기 장치의 인터럽트인지 확인한다.
- 장치 초기화가 끝나기 전에 IRQ가 활성화되지 않게 순서를 설계한다.
- 제거·오류 경로에서는 새 I/O를 차단하고 진행 중인 IRQ/work를 동기화한 뒤 자원을 해제한다.

### 6.3 동시성 제어

예제의 `read/write`는 프로세스 문맥이며 sleep 가능한 mutex를 사용한다. IRQ 문맥에서는 mutex를 사용할 수 없다. IRQ와 프로세스 문맥이 같은 데이터를 공유하면 spinlock, atomic, completion 등 실행 문맥에 맞는 수단을 선택하고 임계 구역을 짧게 유지한다.

동시성 검토 질문은 다음과 같다.

1. 어떤 문맥에서 함수가 호출되는가?
2. sleep 가능한가?
3. 데이터를 동시에 읽거나 변경하는 주체는 누구인가?
4. 장치 제거 중 열린 파일이나 진행 중인 I/O는 어떻게 종료하는가?
5. lock 순서와 콜백 재진입 가능성은 문서화했는가?

### 6.4 Kconfig 의존성과 API 호환성

- `depends on`으로 실제 컴파일·하드웨어 조건을 표현한다.
- `y` 코드가 `m`으로만 존재하는 기능을 무조건 호출하지 않게 한다.
- 새 설정 적용 후 `make olddefconfig`, `make listnewconfig`로 변경을 확인한다.
- 커널 내부 API는 안정된 사용자 ABI가 아니므로 대상 버전의 헤더와 문서를 기준으로 유지한다.
- 이 예제는 Linux 6.4 전후의 `class_create()` 시그니처 차이를 조건부 처리한다. 장기적으로는 대상 커널 버전에 맞춰 불필요한 호환 코드를 정리한다.

## 7. 통합 영향 분석

드라이버를 내장했다고 성능이 자동으로 향상되는 것은 아니다. 모듈 적재 지연을 없애고 초기 사용성을 확보하는 이점은 있지만, 커널 이미지와 상주 코드가 커지며 오류가 부팅 경로에 포함된다.

| 지표 | 통합 전 측정 | 통합 후 측정 | 분석 방법 |
|---|---:|---:|---|
| `Image` 크기 | 기록 | 기록 | `stat -c %s arch/arm64/boot/Image` |
| `vmlinux` text/data/bss | 기록 | 기록 | `size vmlinux` |
| 부팅 완료 시간 | 기록 | 기록 | 동일 보드 조건의 boot log 또는 `systemd-analyze` |
| 가용 메모리 | 기록 | 기록 | 부팅 직후 `/proc/meminfo` |
| 초기화 시간 | 기록 | 기록 | `initcall_debug` 로그 |
| 경고·오류 수 | 기록 | 기록 | `dmesg -l warn,err,crit,alert,emerg` |
| I/O 정확성 | 기록 | 기록 | 정상·경계·동시 접근 테스트 |

비교 시 같은 커널 커밋, 컴파일러, `.config`, 저장장치, 전원 및 부팅 횟수를 사용하고 여러 번 측정해 평균과 변동을 기록한다. 256바이트 교육용 드라이버의 차이는 매우 작으므로 측정 오차를 성능 개선으로 오해하지 않는다.

## 8. 디버깅과 관리 방법

### 8.1 빌드 단계

```bash
make W=1 -j"$(nproc)" Image modules dtbs
./scripts/checkpatch.pl --strict drivers/char/string_buffer/string_buffer.c
make C=1 CHECK=sparse drivers/char/string_buffer/
```

- 컴파일 오류: include, Kconfig 심볼, Makefile 경로, API 버전을 확인한다.
- link/modpost 오류: 중복 심볼, 미정의 심볼, built-in과 module 의존성 방향을 확인한다.
- 메뉴 미표시: 상위 Kconfig의 `source` 위치 및 `depends on`을 확인한다.
- 소스 미빌드: `.config` 값과 상·하위 Makefile의 `obj-*`를 확인한다.

### 8.2 부팅·런타임 단계

- 직렬 콘솔과 이전 정상 커널을 확보한다.
- 필요 시 `ignore_loglevel`, `initcall_debug`, 아키텍처별 `earlycon`을 부트 인자에 추가한다.
- ftrace, dynamic debug, tracepoints로 호출 지연과 실행 순서를 확인한다.
- 개발용 커널에서 KASAN, UBSAN, lockdep, kmemleak를 선택적으로 사용한다. 진단 옵션의 성능 비용을 운영 결과와 분리한다.
- oops가 나면 전체 로그, 커널 커밋, `.config`, `System.map`, `vmlinux`를 함께 보존한다.

### 8.3 제품 수준 관리

직접 수정 파일을 복사하는 방식은 학습에는 적합하지만 제품에서는 변경을 Git 커밋/패치로 관리한다. Buildroot나 Yocto에서는 커널 패치와 config fragment를 보드 레이어에 넣고 CI에서 다음을 검사한다.

- 지원 보드별 defconfig와 전체 빌드
- `W=1`, sparse, Coccinelle, checkpatch 및 정적 분석
- QEMU/실보드 부팅 smoke test와 장치 I/O 회귀 시험
- 커널·DTB·모듈의 동일 release 확인
- Secure Boot/모듈 서명 정책, 버전 관리, A/B 업데이트와 롤백

## 9. 실제 하드웨어 드라이버로 확장

현재 예제는 메모리 기반 문자 장치라 하드웨어 탐색 기능이 없다. Raspberry Pi의 MMIO 장치를 다룬다면 일반적으로 platform driver와 Device Tree를 사용한다.

```text
Device Tree 노드
   compatible, reg, interrupts, clocks
             │ 매칭
             ▼
platform_driver
   probe()  : devm_ioremap_resource, devm_request_irq, 장치 등록
   remove() : 새 I/O 차단, work/IRQ 동기화, 장치 해제
             │
             ▼
문자 장치·IIO·input·netdev 등 알맞은 커널 서브시스템
```

가능하면 임의의 문자 장치 ABI보다 장치 성격에 맞는 기존 서브시스템(IIO, input, hwmon, DRM, V4L2, netdev 등)을 사용한다. 그러면 표준 ABI, 전원 관리, 사용자 도구와의 호환성을 재사용할 수 있다.

## 10. 현재 문자 드라이버에 빠진 기능

실전 제품 드라이버 관점에서 예제에는 다음 기능이 없다.

- 실제 하드웨어의 `probe/remove`, Device Tree 매칭, MMIO, IRQ, DMA
- 여러 장치와 여러 minor 번호 지원
- 프로세스별 컨텍스트 및 열린 파일 수명 관리
- blocking I/O, wait queue, `poll/epoll`, 비동기 알림
- `ioctl`, `mmap` 및 안정된 사용자 ABI 정의
- 전원 관리, suspend/resume, hotplug
- 접근 권한을 설정하는 udev 규칙과 보안 정책
- 통계·상태용 sysfs/debugfs, tracepoint
- 장치 제거와 I/O가 경합할 때의 수명 보장
- fault injection, 동시성·장시간·경계값 자동 시험

이 기능을 한꺼번에 추가하기보다 실제 요구사항과 알맞은 커널 서브시스템을 먼저 결정한 뒤 단계적으로 구현해야 한다.

## 11. 평가 질문 답변

### 커널 모듈보다 내장 드라이버가 유리한 점은 무엇인가?

루트 파일 시스템 접근 전에 필요한 장치, 초기 콘솔, 부팅 필수 기능을 즉시 사용할 수 있고 모듈 파일·로더·initramfs 구성에 의존하지 않는다. 반면 상주 메모리, 커널 재배포 필요성, 부팅 장애 위험을 함께 부담하므로 “부팅에 필수인가”와 “현장 갱신이 필요한가”를 기준으로 선택한다.

### 커널 모듈로 만들기 어려운 기능은 무엇인가?

CPU/아키텍처 초기화, 스케줄러와 메모리 관리의 핵심, VFS·IRQ·시간 계층의 기반처럼 모듈 로더보다 먼저 필요한 기능이다. 또한 부팅에 필수인데 initramfs에 넣을 수 없는 저장장치·파일 시스템 드라이버, 또는 모듈에 공개되지 않은 내부 심볼에 필수적으로 의존하는 코드도 모듈화가 제한된다.

### 커널 통합 설정은 어떻게 선택하는가?

Kconfig `tristate` 심볼과 kbuild의 `obj-$(CONFIG_...)`를 연결한다. `menuconfig`에서 Y/M/N을 선택하고 `.config`의 최종 값을 확인한다. 의존성은 `depends on`을 우선 사용하며 보드 기본 defconfig, config fragment, `olddefconfig`를 통해 재현한다.

### 디버그 및 문제 해결의 핵심은 무엇인가?

빌드·부팅·등록·I/O 단계를 분리하고 각 경계에서 증거를 확보하는 것이다. `.config`, 빌드 첫 오류, `System.map`, 전체 `dmesg`, sysfs와 `/proc/devices`, 재현 입력을 보존한다. 리소스 획득/해제 순서와 실행 문맥을 점검하고 KASAN·lockdep·ftrace 같은 도구로 추측을 검증한다.
